# 《年轮》试听失败修复记录（2026-09-16）

用户反馈旧版歌词混乱、无法辨认，人声比伴奏小。该反馈推翻了此前把
“导出成功 + 音高误差分数”作为可用成品依据的判断。

## 已确认原因与修复

| 原因 | 证据 | 修复 |
| --- | --- | --- |
| 无声帧掩码用反 | 本机 torchfcpe 的 `uv = f0 < f0_min`，1 表示无声 | 取反，保留无声为 0 Hz；按模型 16 kHz / 160 samples 的原生时钟输出，启用新缓存版本 |
| ASR 采样率错 | faster-whisper 的 ndarray 路径绕过解码重采样；原代码输入 44.1 kHz，模型按 16 kHz 解释 | 输入前显式重采样；保留中文歌唱识别仍会错字的限制 |
| 歌词版本错配 | 原录音约 105 秒重唱主歌，旧 LRC 此处安排不同的副歌，且在约 176 秒结束 | 新的录音室版段落与原文件 SHA256 绑定，不再按标题自动匹配 |
| 字时间靠起音数硬分配 | onset 不区分具体歌词，旧流程还把错位歌词移到最近有声块 | 改为现有 Whisper 模型的声学 attention/DTW 逐字对齐；空白 LRC 标记间奏；塌缩字边界明确失败 |
| 量化重叠造成吞字 | 分别四舍五入起点与时长造成 1 tick 重叠；OpenUtau `UNote.Validate` 将后音符标为 Error | 起止边界共用绝对 tick 网格，再减 part 起点；检测重叠与断开的延音；bridge 在导出前拒绝错误音符/音素 |
| 人声电平未匹配 | 旧混音把两轨按固定 0 dB 相加，仅限制总峰值 | 比较有效演唱窗口，匹配参考人声并设置与伴奏的平衡下限，报告实际增益 |
| 分数夸大可用性 | 只对少量可测音符统计误差，漏唱不影响百分比 | 增加全音符准确率与覆盖率，覆盖下降不能胜出；整体质量标记 unverified |

所有修改和试听都在本地完成。保留旧运行与旧 demo；没有发布新音频。

## 验证

- Python 回归与原有测试共 26 项通过，含采样率、掩码、歌词录音绑定、间奏边界、转音毛刺、混音和共享 tick 边界。
- `a2u-bridge` 已重新构建并部署；新整曲原生检查结果：0 错误音符、0 错误音素。
- 新整曲 run：`cover-20260916-102646-95f0`，35 段、631 音符，其中 20 个音符音高证据较弱。
- 274.504 秒完整混音，人声相对伴奏增益 +9.326 dB；合成后两轨共同衰减 3.310 dB 控制峰值，保留相对平衡。
- 当前音高统计覆盖 597/631 音符（94.61%），中位误差 17.4 cents。
  **旧版的 F0 掩码错误，因此不能把旧分数与新分数直接比较。这些数字不证明歌词全部清晰。**
- 改正音符重叠后，前四句可测覆盖从 65/79 增至 73/77；识别回查中此前被吞掉的部分字恢复。
  歌唱 ASR 仍有同音字、漏字，不能将它代替人工听辨。
- 本轮保守使用音符基线、不添加 AP 或额外 pitd；先确认基本歌词与旋律。不是完整自然表现调校。
